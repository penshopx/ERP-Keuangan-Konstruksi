## Implementasi Email Matching yang Benar

```typescript
// 1. Ambil user dari Clerk berdasarkan userId (bukan dari request body)
const clerkUser = await clerkClient.users.getUser(clerkUserId);

// 2. Filter HANYA email yang sudah terverifikasi + normalize ke lowercase
const verifiedEmails = clerkUser.emailAddresses
  .filter((item) => item.verification?.status === "verified")
  .map((item) => item.emailAddress.toLowerCase());

// 3. Cocokkan dengan invitation aktif (juga di-lowercase untuk case-insensitive match)
const [activeInvitation] = await db
  .select()
  .from(invitationsTable)
  .where(
    and(
      eq(invitationsTable.status, "PENDING"),
      inArray(
        sql`LOWER(${invitationsTable.email})`,
        verifiedEmails
      )
    )
  )
  .limit(1);
```

## Implikasi Keamanan

| Risiko jika salah | Dampak |
|-------------------|--------|
| Pakai `emailAddresses[0]` tanpa filter verified | Email belum terverifikasi bisa diklaim → spoofing |
| Ambil email dari request body | Client bisa manipulasi email → klaim undangan orang lain |
| Tanpa lowercase | `User@Example.com` ≠ `user@example.com` → undangan valid tidak ter-claim |

Filter `verification.status === "verified"` memastikan hanya email yang sudah dibuktikan kepemilikannya oleh Clerk yang bisa dipakai untuk matching invitation. Ini menutup celah di mana attacker mendaftarkan Clerk account dengan email orang lain (yang belum mereka verifikasi) lalu mencoba claim invitation.

## Koreksi Kritis: Audit Log dalam Transaksi

Saya mengakui kesalahan konseptual pada catatan sebelumnya. Prinsip ACID yang benar:

### Yang Salah di Catatan Saya
```
❌ "audit log mencatat kegagalan" dalam transaksi yang sama
```

### Yang Benar
Jika audit log berada dalam transaksi yang sama dengan operasi bisnis, maka **ketika transaksi di-rollback, audit log juga ikut ter-rollback**. Ini konsekuensi langsung dari properti *Atomicity* dalam ACID.

### Implikasi untuk Pencatatan Kegagalan

Pencatatan kegagalan transaksi hanya mungkin melalui dua pola:

**Pola A — Transaksi Terpisah (Out-of-Transaction Audit)**
```typescript
try {
  await db.transaction(async (tx) => {
    await tx.insert(projects).values(...);
    await tx.insert(rabHeaders).values(...);
    // jika gagal di sini → rollback
  });
} catch (error) {
  // Transaksi baru, terpisah
  await db.insert(auditLog).values({
    action: 'project_creation_failed',
    error: error.message,
    // ...
  });
  throw error;
}
```

**Pola B — Observability Eksternal (Non-DB Logging)**
```typescript
try {
  await db.transaction(async (tx) => {
    // ... operasi bisnis
  });
} catch (error) {
  // Logger eksternal (file, APM, structured logging)
  logger.error('project_creation_failed', { error, context });
  throw error;
}
```

### Trade-off

| Aspek | Pola A (DB terpisah) | Pola B (Logger eksternal) |
|-------|----------------------|---------------------------|
| Queryable via SQL | ✅ Ya | ❌ Tidak langsung |
| Atomic dengan bisnis | ❌ Tidak (bisa gagal sendiri) | ❌ Tidak |
| Overhead performa | Sedang (1 query tambahan) | Rendah |
| Konsistensi dengan data | Bisa inkonsisten jika logger gagal | Tidak ada inkonsistensi |
| Observability terpusat | ❌ Terpisah | ✅ Bisa integrasi dengan APM |
